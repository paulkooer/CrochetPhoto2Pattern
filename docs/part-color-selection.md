# 部件级选色 V1：规格与验收清单

[English](part-color-selection.en.md) | **简体中文** | [文档索引](README.md)

本文是部件级选色的 V1 规格：先写清数据流、兼容方案、交互与验收清单，再据此实现。
实现状态见文末「实现状态」一节；当前行为始终以源码、`pyproject.toml`、锁文件和
可复现检查为准。相关既有文档：[钩织工程与格式](project-format.md)、
[授权真实照片评测](evaluation.md)、[第三方内容政策](../THIRD_PARTY_CONTENT.md)。

## 1. 目标与非目标

**目标**：用户能主动选择毛线颜色，并让逐圈图解、换线说明、材料清单和能忠实表达的
导出结果保持一致。具体包含：为整个部件选色；为单个实体（如只改左手臂）选色；
为一体头身的头部段与身体段分别选色；提供「设置基础色并保留已有条纹」与「统一换色」
两种明确操作；修改前预览、可应用/取消/撤销/重做；纯颜色修改以保留已完成圈数为目标，
但明确告知已钩出的旧颜色不会改变。

**V1 明确不做**（不是遗漏，而是本轮范围外，见 §11）：

- 按颜色独立的线材小样与不同线材密度（沿用项目现有的统一毛线规格）；
- 圈内（局部）换色与眼斑等附着装饰的自动转换；
- 把 RGB 当作真实毛线色号、批次或用量证据；
- 采集用户操作遥测（人工改色比例与耗时在无真实数据前报告「未评估」）；
- CrochetPARADE 环形起针与跨部件预留半针接合的忠实表达（§12 说明为何不实现）。

## 2. 三个概念的区分

规格必须把下面三件事分开，避免把近似显示当成采购与识别证据：

| 概念 | 在系统中的位置 | 含义与边界 |
| --- | --- | --- |
| **颜色角色** | `params.parts[].name`（部件名）＋ `app/models/parts.py` 的 `_SKIN_PARTS`/`_BODY_PARTS`；占位值 `skin`/`body` | 「这里该用哪一类线」的语义占位（肤色线、主体色线）。它不是某个颜色，也不是色号。V1 **不新增**角色字段：现有部件名与占位值已经表达角色，新增字段只会让人误以为它携带颜色证据。 |
| **实际颜色** | `params.parts[].color`、`params.parts[].rounds[].color`、`params.parts[].instance_colors` | 用户选择或照片识别得到的毛线色名（或用户自定义名）。这是图解唯一实际颜色来源。 |
| **毛线产品** | `params.yarn_spec`（克重/长度/试片）＋ `app/models/colors.py` 的 `brand_code()` 已核实色号 | 采购信息。V1 仍是**一份线标适用于所有颜色**；`brand_code()` 只对已核实条目返回色号，未收录返回 `None` 而不编造。 |

色表中的 RGB 只用于显示色样与近似匹配（CIEDE2000 最近邻），**不构成**色号、批次或
用量证据。材料克数/米数在无线标或实测依据时继续标为估算。

## 3. 数据流

**生成路径（既有）**：照片 → `vertical_color_bands`（逐横带投票）→
`color_blocks_for_part`（按部件纵向占比切段）→ `round_color_plan`（逐圈按重叠量取色）
→ `rounds[].color` → `refresh_color_instructions`（写出部件主色与自动换线片段）
→ `yarn_requirements`（逐色用量）→ Markdown/PDF/Parade/预览。

**人工路径（V1 新增）**：结果页选色 → `app/services/color_selection.py` 的纯函数
→ 改写 `rounds[].color` / `parts[].color` / `parts[].instance_colors` /
`parts[].color_origin` → `refresh_color_instructions` → `refresh_derived`（重算材料、
总针数与时长）→ `rebuild_params`（`CrochetPart` 校验 + `require_valid_pattern`）
→ 进度规则（§7）→ 既有 `edit_history` 预览/应用/撤销/重做 → 全部导出。

人工路径**不得**回写照片证据：`result["color_bands"]`、`vision_meta.color_observation`、
`analysis.recommended_colors`、`analysis.hair_color`/`top_color`/`bottom_color` 保持原值。
人工选择只体现在 `rounds[].color`/`parts[].color`/`instance_colors` 与 `color_origin`，
不伪装成照片识别结果，也不改写照片语义色写下的说明文字。

## 4. 数据模型与单一数据源

**优先级（同一圈的实际颜色，从高到低）**：

1. `parts[].instance_colors[i]`（该份实体的显式选色，非 `null` 时）；
2. `rounds[].color`（该圈的颜色，最高优先级的圈级来源）；
3. `parts[].color`（部件基础色/主色，仅作兜底）。

**新增字段（全部可选、可省略）**：

| 字段 | 类型与约束 | 何时写入 | 含义 |
| --- | --- | --- | --- |
| `params.parts[].color_origin` | `"manual"` 或缺失 | 仅当用户显式选择部件基础色时 | 记录「部件基础色来自人工选择」。缺失仅表示来源未记录，可能是生成色或先前手工修改；不记录逐圈来源（§4.1）。 |
| `params.parts[].instance_colors` | 长度为 `quantity` 的颜色字符串或 `null` 数组 | 用户为某份实体单独选色时 | `null` 表示沿用圈色/部件色。全部为 `null` 或为空时序列化省略；保存实体 ID 后按 ID 对齐，而非仅依赖当前顺序。 |
| `params.parts[].instance_color_ids` | 与 `instance_colors` 等长且不重复的实体 ID 数组 | 有稳定结构实体 ID 时随单份选色写入 | 用于重排后把颜色重新对齐到同一实体；无法保留已选色实体时拒绝该结构变更，先恢复其部件配色才能删除。 |
| `params.parts[].color_section_mode` | `"head_body"` 或缺失 | 用户为一体件头部、身体分别选色时 | 允许尺寸或密度重算时按颈部标记迁移分段颜色；无法确定边界或安全映射时拒绝重算。 |

**`color` 的含义**：生成配色可按逐圈颜色计算主色；手工设置的基础色保留用户的选择，
不会因条纹圈数更多而被覆盖。实际圈色仍按上述优先级确定。

### 4.1 为什么不记录逐圈颜色来源

旧数据没有记录某圈颜色是照片自动生成还是人工指定。仅凭现有字段无法可靠区分：
`rounds[].color` 在两条路径下形态相同，`auto_color_note` 只覆盖**换线边界**，
与「这一圈的颜色是谁定的」不是同一件事。任何启发式猜测都会在用户没改过的圈上
声称「人工」，或在人工改过的圈上声称「照片」。

因此 V1 采取保守策略：**不写**逐圈来源标记，也不据此覆盖任何圈。
「保留条纹」只更新未单独指定颜色、原本继承部件色的圈；所有显式圈色均保留，
即使其值恰好等于旧基础色。「统一换色」按用户明确选择覆盖，并在预览中逐份逐圈列出。

## 5. 兼容与迁移

- **备份顶层版本升为 `schema_version="2"`**。未标版本及版本 1 的旧图解可通过迁移链
  读取；版本 1 到 2 不猜测颜色来源。旧应用遇到版本 2 会明确拒绝，避免重新保存时丢失
  不认识的选色字段。
- **必须声明在 `CrochetPart` 上**。`rebuild_params` 走
  `CrochetPart(**part_input)` → `to_data()`，未声明的键会被 pydantic 静默丢弃
  （已复现：`instance_colors`/`color_origin` 不在模型上时，`to_data()` 里没有这两个键）。
  因此新字段必须进模型，并由
  `docs/schemas/crochet_part.schema.json` 漂移测试守护。
- **旧备份读入**：沿用其部件数量和已有圈色，不猜测、不自动补写来源。
- **校验**：`instance_colors` 长度必须等于 `quantity`；不满足时在 `rebuild_params`
  边界拒绝（不静默截断），实体 ID 的长度和唯一性也会校验。单份选色需要稳定的图
  实例 ID；删除已单独选色的实体前须先恢复其部件配色。旧的无 ID 数据只能沿当前份序
  接受，历史归属无法验证。
- **载体覆盖**：备份、分享 token、本机历史、工程文件、试钩包都经
  `PatternResult`/`rebuild_params` 同一契约，新字段随 `params.parts[]` 自动往返。
  工程进度绑定图解修订（`pattern_revision`）；人工选色改变图解 → 修订变化 →
  进度按 §7 判定。备份、分享、工程和新建试钩包会剔除 `preview` 与 `geometry.mask_review`；
  启用的单用户历史在部署主机保存这两个字段，恢复的旧试钩包则原样保留其原图解字节。
- **导出缓存**：导出内容（含逐色/逐份颜色）变化时提升。本轮由 **17 升至 18**，
  旧会话的 Markdown/PDF/Parade 需重新生成。导出缓存当前值见
  `app/ui/export_cache.py` 的 `EXPORT_CACHE_VERSION`。
- **工程修订**：版本 1 到 2 不改变旧图解语义；恢复时兼容原有修订哈希。`project_state`
  与试钩记录各自独立版本化，均未改动。

## 6. 交互

入口：结果页第 5 章「局部修正」→「毛线选色」折叠面板（与留口、独立密度、接裙等
专项工具同层）。所有提交都走既有 `edit_history`：可预览影响、应用、取消、撤销、重做。

1. **选择部件**：下拉列出全部部件，标签包含部件名与当前基础色（占位值按
   `app/utils/color_labels.py` 显示为「肤色（待选色）」等）。
2. **选择颜色**：色表下拉（`app/models/colors.py` 的 `YARN_COLORS`）或「自定义」文本输入
   （保留用户自定义名，与逐圈表格编辑器一致）。
3. **选择操作**（二选一，必须显式选择）：
   - **设置基础色并保留已有条纹**：把继承部件基础色的圈改为新色；所有显式圈色
     **一律保留**，并在预览中列出「已保留的圈」。
   - **统一换色**：把该部件全部圈改为新色。这会覆盖逐圈已有颜色（含条纹与人工
     修改），预览中**逐圈列出**旧色与新色，要求用户确认后应用。
4. **实体选色**（`quantity > 1` 且存在稳定 ID 时）：选择「仅所选实体（整份统一
   换色）」与对应实体；也可选择「恢复部件配色」移除该份覆盖。整件统一换色会清除
   各份覆盖，界面事先提示；缺少稳定 ID 时不开放单份选色，并提示可选择整个部件。
   若新生成的图解具有稳定身份，可单独选色，但旧实体的对应关系仍需核对。
5. **一体头身分段选色**：当部件为 `头身（一体）` 时，提供「头部段颜色」与
   「身体段颜色」两项。分段边界取 `app/models/parts.py` 的
   `ONE_PIECE_NECK_MARKER`（生成器在唯一一圈说明中写下该标记，`crochetability`
   与 `skirt_edit` 已按同一标记解析）。**标记缺失或不唯一时拒绝操作并提示**，
   不凭文本猜测边界。
6. **预览**（应用前必看）：列出部件、实体、受影响圈次（圈号/旧色/新色）、
   已保留的圈、逐色材料用量前后对比、进度影响（沿用
   `progress_state.progress_impact`），以及本节的进度与已钩部分提示。
7. **必须明确的提示**：
   - 已钩出的旧颜色不会因为图解改色而改变；勾选记录不代表实物无需返工。
   - 统一换色会覆盖已有逐圈颜色，且被覆盖的圈在应用后无法从界面恢复原值
     （只能用撤销回到修改前）。
   - 3D 预览只按部件主色示意，不显示逐圈条纹或分部实体颜色（§8）。
   - 色表外的自定义颜色只用于图解与显示，不提供色号或用量依据。

## 7. 进度规则

**默认（既有保守规则不变）**：`progress_state.progress_limits` 比较部件的完整说明
（含颜色）与逐圈说明（含颜色，缺失时回退部件色）；从首个受影响圈起清除完成记录，
接合与装配依赖仍按既有规则传导。

**V1 新增的例外，仅对「已验证的纯颜色修改」生效**：若两份图解除颜色承载字段外
完全相同，则全部已完成圈次保留。判定条件（全部满足才算纯颜色修改）：

- `parts[].color`、`rounds[].color`、`parts[].instance_colors`、
  `parts[].instance_color_ids`、`parts[].color_section_mode` 和 `parts[].color_origin`
  可以不同；
- 逐圈 `auto_color_note`、部件 `auto_color_summary`，以及 `notes` 中**等于**
  这些已记录自动片段的那一段，可以不同（它们是由颜色重新推导的）；
- 其余一切必须完全相同：`name`、`type`、`quantity`、`rounds` 的圈号/针数/加减针/
  `region`/`height_range_cm`/`allow_wide_jump`、`notes` 中的人工文字、`opening_row`、
  `magic_ring`、`gauge`、`params.gauge`、`stitch_attachments` 与 `assembly_plan`；
  各部件每份实体的身份顺序（结构实例 ID）也必须相同。

只要针数、针法、连接或其他施工发生变化，仍按原有保守规则处理。

**两处有意保守的例外**：

- **跨部件预留半针接合**涉及的部件即使只改颜色，也沿用原有保守规则：这类部件的针目
  身份取决于被接的一方，已有测试钉住了该契约。纯颜色的整段保留只作用于未参与接合的
  部件，其余部件仍按逐圈比较与接合依赖传导处理。
- **实例顺序或数量变化**不算纯颜色修改：逐圈针数可能一字未改，但完成记录归属的实物
  变了。判定包含每份实体的身份顺序，因此结构实例重排会照旧清除受影响部件的进度。

**为什么不做全局放松**：现有比较包含颜色，正是为了防止「改了颜色却仍显示已完成」
的误判；已有测试也验证了关联部件的保守失效。只对可证明的纯颜色修改放宽，可以保留
已完成圈数，同时不放过任何施工变化。

**提示义务**：无论是否保留进度，界面都必须说明「已钩出的旧颜色不会因为图解改色而
改变」。保留进度只表示**图解其余部分**无需重新核对，不表示实物与图解已经一致。

## 8. 导出与一致性

| 载体 | 是否体现颜色修改 | 说明与限制 |
| --- | --- | --- |
| Markdown | 是 | 部件「颜色」行、圈表「配色」列；存在 `instance_colors` 时按份列出该份颜色，并把「N 个相同部件」改为「N 个同针法部件（配色见下）」。 |
| PDF | 是 | 同 Markdown 的部件颜色与圈表配色列（PDF 另列部件基础颜色）。 |
| 材料清单 | 是 | 逐色克/米/团；存在 `instance_colors` 时按份归属针数，逐份颜色分别汇总。无线标或实测依据时仍标为估算。 |
| CrochetPARADE DSL | 是（在本项目已核对的子集内） | 每份实体各自输出 `COLOR:` 前缀与逐圈换色边界；无法转换的自定义颜色（含来源未记录的旧圈色）或不支持的构造会报告未完整导出，不能冒充原色导出成功。 |
| 3D 结构预览 | 否 | 仍按部件主色取示意色；**明确标注**不显示逐圈条纹与分部实体颜色。 |
| 试钩包 | 是 | 内嵌图解备份，保留图解颜色；试钩记录的格式独立。 |
| 平面网格工程 | 不变 | 使用独立的网格与色板格式。 |

一致性的可验证含义：对同一 `result` 同时生成 Markdown、PDF 材料行与 DSL 文本，
逐圈颜色与逐色汇总必须互相吻合；不一致即为缺陷。颜色变化不改变针数、总针数、
时长或施工说明（自动换线及配色摘要会随颜色刷新）。

## 9. 评测指标

以下四项为后续评测设计。每项写出定义、分母、缺失标签处理与数据来源。
**人工改色比例**与**配色修正时间**必须来自真实用户操作，不能由合成测试推断。

| 指标 | 定义 | 分母 | 缺失标签处理 | 数据来源 |
| --- | --- | --- | --- | --- |
| **部件颜色匹配率** | 将每个已标注部件或实体的预测颜色与对应人工颜色真值比较；预测缺失或对应错误计不匹配。自动结果和人工修改后结果分开报告。 | 有可比部件级颜色真值的部件或实体数 | 无部件真值者排除并记录数量；全部缺失时报告「未评估」 | 未来经授权的逐部件标注与对应管线产物；现有全图 `dominant_colors` 不能代替部件标签 |
| **人工改色比例** | 在可观察的真实使用会话中，用户至少修改一次配色的部件或实体占比。 | 该会话中可观察的部件或实体数 | 无真实会话或无法还原操作时报告「未评估」；缺少来源标记不能视为未修改 | 经用户同意的会话前后记录；V1 不采集遥测，保存结果不能独立证明所有操作 |
| **配色修正时间** | 用户从看到生成配色到应用最终选色之间的实际用时。 | 完成选色的真实用户会话数 | 无真实会话时报告「未评估」 | **V1 不采集**。若日后实现，必须本地、明确告知、由用户主动选择开启；不得默认开启 |
| **页面/图解/PDF/材料清单一致性** | 同一 `result` 的页面显示、Markdown、PDF、材料清单在逐圈颜色与逐色汇总上完全一致的比例。 | 参与比较的部件与颜色条目数 | 缺少某一导出载体时该案例不计入，并记录跳过原因 | 自动化一致性断言（`tests/*`）＋ 浏览器回归证据 |

补充约束：保留 Beta 定位；授权照片、实体试钩与独立验证尚未完成，**不得**用自动化
测试或合成图片替代 G3/G4 证据。这些指标衡量软件行为，不证明实际尺寸、用线量、
工时或成品可钩性。

## 10. 验收清单

- [ ] 整件选色：两种操作语义正确；「保留条纹」不覆盖显式圈色；「统一换色」覆盖全部圈和逐份覆盖并在预览逐圈列出。
- [ ] 实体选色：`quantity > 1` 时只写目标份；`parts[].color` 不变；材料按份拆分；界面显示实体 ID。

## 11. 未完成与已知限制

- **旧数据的实体归属可能无法考证**：新单份选择绑定稳定结构 ID；旧文件如果只有
  序数、没有 ID，只能沿用当前份序，不能证明历史归属。缺少稳定 ID 时不开放新单份选色。
- **一体头身分段选色依赖颈部标记**：手工构造且没有该标记的一体件不支持分段选色。
- **3D 预览仍是部件级主色示意**，不显示条纹与逐份颜色。
- **无逐圈颜色来源标记**（§4.1）：无法在界面区分某圈是照片生成还是人工指定。
- **不支持按色独立小样/不同线材密度**；仍是一份线标适用于所有颜色。
- **不支持圈内（局部）换色**；照片中的局部斑块仍只作证据显示，不自动转成圈内换色。
- **人工改色比例与配色修正时间**在无真实用户数据前报告「未评估」，不填 0、不声称准确率提升。
- **CrochetPARADE 环形起针与跨部件预留半针接合**仍是导出能力缺口（§12）。

## 12. CrochetPARADE 差距的核对结论（本节未实现）

**结论：本轮不实现环形/锁针起针的忠实表达。**理由是未能取得可证明语义正确的官方依据。

已核对的依据全部来自本仓库既有的来源记录（[SOURCES.md](SOURCES.md)），**不是**
本轮的新核实：官方 HTML 手册的 stitch table、`stitch_nameNinc/Ntog`、能力说明 §1.5
用于核对 `scfl`/`scbl` 与增减后缀；`Manual.md` 用于核对「每行一圈、按前圈顺序连接
针目及重复组」；`start_anew` 表示下一针与前一针无连接。既有记录同时明确写下
「**缺少基底的首圈挑针同样不按魔法环猜译**」与「文字错位提示、挑针、**非魔法环起针**
及收口动作仍需对照原说明核对」——即该构造属于**已知未翻译**项，与 `parade_export.py`
的 F-10 标记一致。

本轮尝试联网复核官方手册与能力说明时，请求被服务端限流（HTTP 429）拒绝，**无法**
重新核对；因此没有新的官方语法依据支撑「开口筒起针」的实现。

不实现的具体理由：

1. 现有 DSL 子集里没有任何指令的**已核对语义**是「开口起针」。`ring` 单独一行是魔法环
   （无固定默认针数），按它导出开口筒就是把开口换成闭合圆盘——语义不符。
2. 输出 `ch`/`ss` token 不构成证据。本项目 lint 的 token 白名单来自我们自己的核对于集，
   **不是** CrochetPARADE 官方 parser（模块文档已声明它不是官方 parser）。词表里出现
   `ch` 不等于上游翻译器会把「锁针成环 + 挑针进入环」执行成一个开口筒。
3. 把开口筒静默近似成闭合圆盘会给出错误的 3D 与张力结论，比诚实跳过更有害。

**实现方案（条件式，待证据齐备后执行）**：需要的证据是（a）官方手册或能力说明中
一条**其文档含义明确为开口基底**的指令（锁针成环、引拔连接成环，或明确支持把针目
钩入锁针链），以及（b）能表明上游翻译器实际执行该构造的依据（官方示例或官方说明），
两者都要能逐条引用。证据齐备后按以下步骤实施：在 `_part_lines` 中按部件构造选择起针
指令；对开口筒输出该指令而非 `ring`+`scNinc`；把对应的 `unsupported_constructions`
条目改为不再登记（或改写为已支持）；同步更新 `docs/SOURCES.md` 的来源记录、
`docs/evaluation.md` 的口径与 `test_parade_export_counts.py` 的口径测试。
**在证据齐备之前，导出器继续把该构造登记为 `ring_start` 并不计入完整导出实体数，
且不虚构 DSL 指令、不把开口筒静默替换为闭合圆盘。**
