## 2. 用户真正关心的问题

用户想从复杂穿衣玩偶照片得到可以照着制作、结构与目标接近的图解。当前简单几何模板
与真实成熟图解差距明显。用户已决定颜色后放，优先看钩法、结构、连接和生成方法是否成立。

请分别回答，不能合成一句“系统通过”：

1. 现有输出有哪些会让制作者卡住、做错或误判完成状态的确定性缺陷？
2. 当前工序表达和尺寸设计能支持哪些构造，哪些仍靠人工、假设或未表达的步骤？
3. 界面是否让用户理解“照片辅助模板”“人工选型原型”“参数化工序设计”的区别？
4. 软件审查后，是否适合开始某个明确的局部样片？还缺什么条件？不能仅凭代码就认证
   整件可钩、合身或能还原照片。
5. 为逼近用户目标，接下来最该做哪三件具体工作，各自用什么结果验收？

这次不做竞品/论文综述，不优先扩展形状族、调配色或接入 3D 后端。颜色处理若涉及
数据损坏、输入安全或错误状态仍应报告；颜色精度优化排在结构正确性之后。

## 5. 审核重点与应尝试的反例

以下是待证伪的问题，不表示每条目前都有缺陷。先检查真实调用路径，再用最小反例区分
违反已声明契约的 bug、明确不支持的构造、尚缺证据的设计假设与未来功能。

### A. 旧流水线与本轮兼容性

- `assembly.py`、`crochet_params.py`、`materials.py`、`stitches.py` 及 Markdown/PDF：
  安全眼是否确实先于填充和封口；头顶、头底和眼位是否统一；裙筒试套是否在无法穿入之前。
- 检查 `construction_guidance_version`、`refresh_derived`、旧工程导入、分享、恢复与
  试钩图解字节绑定。旧稿是否被静默改写，新稿是否在编辑后退回旧说明或丢失必要说明。
- 部件增删、改名、改尺寸、改密度、头身一体、留口、跨部件连接后，逐圈表、装配、材料、
  进度、指纹与导出是否仍对应同一结果。抽查本轮修改的 102 个输出快照，不能把刷新夹具
  本身视为兼容性证明。

### B. 工序模型是否接受了自相矛盾的输入

- 检查 `Span`、`Hold`、`EdgePath` 的原始针位和别名归属：越界、重叠、重复占位、
  转移后旧别名、倒序/跨段拼接、非相邻来源是否可能绕过约束。
- 区分锁针两面、FLO/BLO、行端、转角引用与真正新织物针位。是否能凭空制造可用位置、
  重复预留半针，或用留边声明隐藏本应处理的连接缺口。
- 连续翻面行的实际来源顺序、正反面与当前环是否一致；跨分段、引拔闭合、起链后翻面
  是否仍成立。不要把单一 `section` 中的检查误认为一般几何连续性验证。
- 另接线、暂停、恢复、断线、藏线是否有完整的状态检查；尝试错误锚点、复用线段名、
  从暂停线直接工作、从接缝另一端开钩、漏转面及用声明收边替代收线。
- 构造一个“针数相等但无法按导出文字继续”的最小反例，比重复已有正确案例更有价值。
  同时区分本协议的限制与一般钩织技法的有效性，不能用程序拒绝断言现实中不可钩。

### C. 从尺寸生成工序的规则是否合理且透明

- 领口、衣身展开宽、袖围与肩深是否一起约束五段配针；允许的针数调整和奇数行量化
  是否正确报告。检查边界值、非默认尺寸及无法同时满足的情况。
- 沿边肋纹行数、针宽、1/2 位接合分配是否与基底长度和独立肋纹密度一致。
  起链根部与末端是实际设计余留，还是隐藏的 off-by-one。
- 门襟工作边的分段顺序与连续性，行侧每行挑一位的假设，领口与扣眼位置、镜像纽扣
  位置、扣眼宽度及末端接续是否清楚；不能从链数直接认证纽扣可穿过。
- 衣身到下摆、门襟到袖子、袖子到袖口、袖口首末行接合是否有具体可执行步骤。
  左右袖、奇偶行和不同袖长应分别检查。
- 缺密度、密度来源不同、尺寸量化到零/越界、后续阶段失败时，是否返回正确阶段和
  缺口，是否残留看似完整的可下载稿，是否悄悄补入默认模板。
- `hypothetical`、`reference_declared`、`user_entered_swatch` 是数据来源声明，用户输入
  数值不表示助手实测；统计结果、UI 与导出是否始终保留这种区别。

### D. 穿衣原型是否只换了部件标签

- 独立核对魔法环、起链环、片钩、椭圆底、发束回钩、袖窿留边和装配长度单位。
- 头与手都使用圈钩并非自动构成缺陷；应检查实际轮廓、掌腕转折、鞋头鞋跟与衣物
  构造是否符合输出承诺，不能用“针法不同”代替目标结构成立。
- 帽檐、发帽与帽围、衣服与身体、鞋口与腿围、裙腰与身体的余量是否有依据；只有
  针数自洽时，哪些结论必须留给制作与试穿。
- 检查装配图中的去向与逐步说明是否一致；引用存在、图无环不代表用户已知道怎样缝合。

### E. 界面、导出与失败恢复

- 在手动页依次检查开衫设计、穿衣原型、人工工序阅读三个入口。尝试改尺寸、换模式、
  载入 JSON、失败后重试、准备 PDF 后继续修改，以及多个结果交替操作。
- 旧结果可查看时，下载是否明确绑定旧输入；输入、引擎版本或输出语义改变后是否
  仍能误下载过期文件。一次点击是否实际影响另一个模块的 session state。
- JSON、Markdown、PDF 与界面表格能否互相对照到相同针位、圈行、锚点、转面、
  暂停与收尾；是否有术语混淆、未解释缩写、表格截断、过长公式或关键步骤被省略。
- 解析、生成、PDF、写盘失败及已有目标文件时，是否覆盖旧稿、留下误导性半份结果，
  或显示成功但实际缺文件。单独区分“生成前失败无输出”和任意 I/O 失败的原子性。
- AppTest 通过和既有 browser-smoke 通过，不能自动说明新入口每条交互都已走真实浏览器。
  报告必须列明实际操作过的入口和动作。

### F. 全系统数据、安全、评测和维护性

- 工程/备份/分享/历史、网格编辑、制作进度及试钩恢复：身份隔离、不可变快照、旧格式
  迁移、错误输入、失败重试与跨结果串数据。
- 图像/JSON/ZIP 输入大小、重复键、非有限数、深层嵌套、解压与图片解码、错误信息和
  日志，是否存在可触达的损坏、泄露或失控资源消耗。
- `app/evaluation.py`、`app/trial_tools/`、导出器、发布证据脚本和 CI：门槛有没有被
  占位检查、宽松模式、测试虚构完成记录、同一设计泄漏或旧收据绕过。
- 层依赖、重复实现与异常处理，仅在说明具体错误路径、维护成本或迁移风险时提出
  重构建议；不要因文件长而建议先大规模重写。
